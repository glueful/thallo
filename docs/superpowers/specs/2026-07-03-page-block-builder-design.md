# Page/Block Builder — Design

**Date:** 2026-07-03
**Track:** V2 §6 "page/block builder" (the final deferred track)
**Depends on:** the content primitive (`FieldDefinition`/`FieldValidator`/entry JSON storage), the render pack (template hierarchy, `RenderContextExtension`, preview sessions), and the shipped DB-edited-templates policy layer (`TemplatePolicy`, spec 2026-07-03) for the sandbox-allowlist addition.

## 0. Decisions (from brainstorm)

| Decision | Choice |
|---|---|
| Authoring UX | **Structured block-list editor** (Sanity/Strapi style) in the entry editor — no visual canvas; real appearance checking goes through preview sessions. |
| Block definitions | **Global block-type registry** (`lemma_block_types`): admin-defined mini-schemas reusing `FieldDefinition`, shared across content types, one theme template per block type. |
| Storage | Blocks are a **normal content field**: an ordered JSON list inside entry `fields` — drafts, versions, rollback, publish, localization, preview, and delivery are untouched. |
| Nesting | **None in v1** — enforced at block-type save (see §2). |
| Localization | **Outer field only** — a localized `blocks` field means one ordered block list per locale. |
| References in blocks | **Validated, never auto-expanded** in v1 (see §5). |
| Schema evolution | **Non-migrating** (see §3). |
| Block-type removal | **Deactivate, not delete** (see §2). |

## 1. Data model

### The `blocks` field type

`'blocks'` joins `FieldDefinition::TYPES`. A blocks field's stored value:

```json
[
  { "id": "b1a2c3d4e5f6", "type": "hero", "data": { "heading": "…", "image": "asset-uuid" } },
  { "id": "f6e5d4c3b2a1", "type": "quote", "data": { "text": "…", "attribution": "…" } }
]
```

- `id` — a stable nanoid, generated by the editor when a block is added (the server generates one on save if missing); **unique within the list** (validated). Stable across reorders — it's the reorder/drag key and the future anchor-link hook.
- `type` — a block-type slug from the registry.
- `data` — an object validated against that block type's field schema.

`FieldDefinition` gains one optional property for blocks fields: `blockTypes: list<string>` — **controls which active block types the admin picker offers**. Empty/absent = all active block types. **It is not a server-side validation constraint** (§4 — the validator accepts any known block type). `blocks` is **not filterable** and not a valid `filterType`; `localized` applies to the whole field (pin: per-locale = per-locale *ordered list*; there is no per-field localization inside a block in v1 — block schemas reject `localized: true` fields at save).

**Every schema surface carries the new type/property (pinned — the type must round-trip, not merely parse):**

- `FieldDefinition::TYPES` gains `'blocks'`; the class gains `blockTypes`.
- `FieldDefinitionData` (request DTO) gains `block_types` input + `toArray()` passthrough.
- `FieldSchemaData` (response/OpenAPI DTO) gains the field, so the generated admin client types it.
- `ContentTypeSchema::toArray()` preserves `block_types`.
- `FieldType` enum gains a `Blocks` case.
- `EditorialFieldTypes` registers `content.blocks` with `filterable/sortable/indexable = false`, `multi = true`, `localized = true`, admin widget `blocks-editor`.

### The block-type registry

`lemma_block_types` (in-app — this is content-schema machinery, `App\Content`, NOT a render-pack concern):

- `uuid`, `slug` (unique), `label`, `icon` (nullable — a lucide icon name for the picker), `description` (nullable), `schema` (JSON: the same field-definition shape content types use), `active` (bool, default true), timestamps.

Admin CRUD at `/v1/admin/block-types`, authorized exactly like content-type schema management (`routes/lemma_admin.php` precedent — no new permission is invented): **read routes carry `lemma_permission:content.view`, mutating routes carry `lemma_permission:content.manage`**, behind the standard `auth` group. Slugs are immutable after creation (they're the template-file contract: `blocks/{slug}.twig`).

## 2. Block-type schema rules (validated at block-type save)

- Fields reuse the full `FieldDefinition` vocabulary **except**:
  - `type: 'blocks'` is **rejected** — no blocks inside block schemas in v1 (the no-nesting pin is a validation rule, not a convention).
  - `localized: true` is **rejected** — localization belongs to the outer field (pin).
  - `filterable: true` is **rejected** — block data is never a filter surface.
- **Deactivate over delete (pin):** block types carry `active`. Deactivating removes the type from the add-picker; existing entries containing it keep validating, editing, and rendering. There is **no hard delete in v1** (usage counting inside versioned JSON is expensive and driver-specific; hard delete can be an admin-only cleanup later).
- Reactivation is allowed; slug immutability makes it safe.

## 3. Schema evolution (non-migrating — pinned v1 policy)

Block types inherit the content-type schema-evolution problem. v1 pins:

- Schema edits affect **future validation only**; existing entry/version JSON is **never migrated or rewritten**.
- On save, each block's `data` is returned as a **cleaned payload** — known fields only, in schema order — exactly `FieldValidator`'s existing rule for top-level fields. Keys not in the current block schema are therefore **stripped on the next save** of that draft; historical versions keep them untouched (read returns stored JSON as-is).
- Removing a field from a block schema does not rewrite old versions.
- **No rename/retype migration** for block-schema fields in v1.

## 4. Validation (draft save + publish)

`FieldValidator` handles `blocks` values:

- The value must be a list of `{id, type, data}` objects; anything else is a field-level error.
- `type` must be a **known** block-type slug (active OR inactive — inactive blocks in existing content must keep saving); **unknown slugs are rejected**. The field's `blockTypes` allowlist is a **picker constraint only**: the validator accepts any known block type regardless of the allowlist, so tightening an allowlist never strands existing content (the same non-migrating tolerance as deactivation and schema evolution — the server cannot distinguish "predates the change" from "newly added", so it does not try).
- `data` validates against the block type's schema **per block, with dot-path errors**: `body.2.heading` (index, then field), same 422 envelope as everything else.
- `$strict` (publish gate) threads through: present-but-empty required block fields and **dangling references inside block data** reject at publish, not at draft — the exact top-level semantics, one level down.
- Duplicate `id`s within the list: error. Missing `id`: server generates.

## 5. References and assets inside blocks (pinned v1 rule)

Reference/asset fields inside block schemas are **validated** (type shape, publish-time dangling checks) but the delivery API and the render context return the **raw stored value** (UUID or UUID list). There is **no automatic expansion**: `ReferenceResolver` scans top-level schema fields only, and this spec does not change that. Consumers:

- **Themes** resolve entry references with the existing `path(uuid)` Twig function where a link is needed.
- **Headless clients** fetch referenced entries themselves.
- Nested expansion (selector syntax, access checks, depth limits) is an explicitly deferred follow-up — the spec must never imply nested references expand "because normal fields do"; they don't.

Cache note (unchanged behavior, stated for clarity): rendered pages tag `lemma:entry:{uuid}` for the page's own entry only. An edit to an entry referenced *inside a block* does not purge pages embedding it — identical to today's top-level reference behavior; out of scope.

## 6. Rendering

A `blocks(list)` function on `RenderContextExtension`:

- Iterates the list in order; each block renders through the environment loader at **`blocks/{type}.twig`** — the normal hierarchy applies: app-theme file overrides nothing-else-exists, and **DB-edited templates work automatically** (block templates ride the same `RenderTemplateLoader` chain).
- **Pinned per-block template context:**

```php
[
  'block' => ['id' => …, 'type' => …, 'data' => […]],
  'data'  => […],          // convenience alias of block.data
  'entry' => …,            // the CALLER's entry context, passed through (null when absent)
  'index' => 0,            // 0-based position in the list
]
```

`blocks()` is registered `needs_context`: it forwards the calling template's `entry` variable into each block template (null on contexts without one, e.g. a listing page experimenting with blocks). Block templates must treat `entry` as read-only ambient context, exactly as page templates do.

- **Missing template (pinned):** production renders an HTML comment (`<!-- lemma: no template for block "hero" -->`); debug renders a visible placeholder naming the block type and expected path; either way the miss is **logged once per block type per process**, not per block instance.
- Malformed block entries (non-array, missing type) are skipped with the same log-once treatment — a template never explodes over data.
- **No shipped block templates in v1**: block types are admin-defined, so the pack cannot ship matching templates. The placeholder + README document the `blocks/{slug}.twig` convention; theme authors (or the DB template editor) supply them.
- **Sandbox policy dependency (pin):** `blocks` joins `TemplatePolicy::FUNCTIONS` and `TemplatePolicy::CACHE_VERSION` is **bumped** — this spec depends on the shipped DB-edited-templates policy layer. (Had blocks landed first, this would have been a plain render function with no policy step.)
- Tag collection: `blocks()` renders within the page's render — collected facet/etc. tags keep working; blocks add no new tag semantics in v1 (see §5 cache note).

## 7. Admin SPA

**Blocks widget** (a `blocks` entry in the `FieldEditor` registry):

- Vertical list of **block cards**: collapsed header showing the block type's icon + label + a text summary (first non-empty string/text value in `data`); expand to edit the block's fields with the **existing field widgets** (a block schema is just `FieldDef[]`).
- **Add-block picker**: searchable list of ACTIVE block types, filtered by the field's `blockTypes` allowlist.
- Reorder: up/down buttons + drag handle; duplicate; delete (with confirm). Collapsed by default; `data-test` hooks throughout.
- An inactive block type already present in the content renders its card with an "inactive" badge — editable and reorderable, but not re-addable.

**Block types admin screen** (`settings/block-types`, beside content types): list with active toggle; create/edit form — slug (immutable after create), label, icon, description, and a schema editor reusing the content-type builder's field-definition UI, with `blocks`/`localized`/`filterable` options absent per §2.

## 8. Error handling (consolidated)

| Failure | Behavior |
|---|---|
| Block-type schema containing `blocks`/`localized`/`filterable` fields | 422 at block-type save |
| Duplicate/unknown block-type slug at registry save | 409 / 422 |
| Unknown block `type` in entry data | 422 (dot-path) at draft save |
| Block `data` field invalid | 422 with `body.{index}.{field}` paths |
| Dangling reference inside block data | passes draft, 422 at publish (strict) |
| Missing `blocks/{type}.twig` | prod HTML comment / debug placeholder; log once per type |
| Malformed block instance at render | skipped; log once |
| Deactivating an in-use block type | allowed by design (renders/edits continue) |

## 9. Testing

- **Backend:** `FieldValidator` blocks cases (list shape, unknown type rejected, known-but-outside-allowlist type ACCEPTED — picker-only rule, dot-path data errors, duplicate ids, id generation, strict-publish dangling refs inside blocks, cleaned-payload stripping of removed schema keys); block-type registry CRUD (slug immutability, schema rules §2, deactivate semantics); OpenAPI regen assertions for the new admin endpoints.
- **Render:** `blocks()` order + context shape (`block/data/entry/index`), theme-file override, **DB-template override of a block template**, missing-template prod/debug behavior + log-once, malformed-instance skip, sandbox allowlist (a DB template calling `blocks()` lints clean; `CACHE_VERSION` bumped).
- **SPA:** widget add (picker filtered to active + allowlist), reorder, edit-with-existing-widgets, duplicate/delete, inactive badge; block-types screen CRUD; `pnpm gen:api && type-check && test`.

## Out of scope (v1)

- Nested blocks; per-field localization inside blocks.
- Automatic reference/asset expansion inside block data (deferred with selector syntax + access checks).
- Block-schema migrations (rename/retype); hard-deleting block types.
- Visual canvas editing; per-block style controls; shipped block template library.
- Purging pages on edits to entries referenced inside blocks.
