# Visual Builder Phase C.1 — The Blocks Tab Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One palette for the Design page — a Blocks tab in the inspector that lists every active block type, inserts by click at an armed target, and drags a new block onto the stage through the coordinator — replacing the stage's add-after popover; the block list's gaps and the outline's empty slots arm that same tab.

**Architecture:** the palette is a fourth drag source for the coordinator that already exists (spec §5.1 names it: palette, outline, stage). A palette drag begins a coordinator session with `{ block }` (the factory's instance), the parent keeps the pointer through pointer capture, converts viewport coordinates to the iframe's and drives the bridge's parent-originated drag messages (`drag-begin` / `drag-hover` / `drag-end`, shipped in B6.2), the bridge answers with proposals, the coordinator judges each one with `checkInsert`, and the drop records one `InsertBlock`. Click insertion is the same session without movement: an armed target is a zone the Blocks tab remembers until a card is clicked, Escape is pressed or the selection changes. Nothing else changes: the factory, the coordinator, the legality rules, the bridge geometry and the proofs' world all stay as B6 and B7 left them.

**Tech Stack:** Nuxt UI admin (Vue 3, vitest, Playwright for the builder proofs), the render pack's preview bridge (plain script). No PHP changes.

**Spec:** `docs/internal/superpowers/specs/2026-09-14-visual-builder-design.md` — §5.1 (the palette as a source), §5.2 (legality), §5.3 (proposals), §5.5 (insertion through the factory), §5.6 (proofs). Phase B shipped in beta.31 (`docs/internal/plans/2026-09-15-visual-builder-phase-b-plan.md`); its names are reused verbatim. This item is the first entry of OUTSTANDING section E, filed at the end of Phase B.

## Global Constraints

Every Phase B global constraint applies unchanged. The ones this plan leans on:

- **The block tree is the source of truth; the DOM supplies geometry only.** A palette drag moves nothing until its drop yields an operation; a click at an armed target is a drop with no movement.
- **Whole-candidate-tree legality before any structural commit.** A palette proposal is judged by `checkInsert(doc, position, block, ctx)` on the factory's instance, starter blocks included, so a starter that nests (a section's empty content slot is a subtree of height 1, a preset that ships children is taller) counts against the depth cap at the destination.
- **The builder is stricter than the API.** The Blocks tab lists every active type; whether a type may land somewhere is the destination's business. A card whose type the armed target's allow-list refuses is shown disabled with the reason, never hidden, so the user learns why.
- **Insertion is `InsertBlock(type, starter)` from the server block factory** (§5.5). The palette never constructs a block inline; `useBlockFactory().instance(slug)` is the only source, prefetched on pointerdown so a drop rarely waits on it.
- **No legacy code, no compatibility.** The stage's add-after popover, its virtual-reference anchoring, its filter and its tests leave in the same commit that arms the Blocks tab. `BlockInsertMenu.vue` stays: it is the picker of ordinary `BlocksField` editing outside the Design page and of the prose editor's `/` split, which the Design page does not replace (the same boundary Phase B drew for `BlockOutlineRail.vue`). Inside the Design page the list's gaps arm the tab and never open that menu.
- **One code path for ordering and filtering the types.** The category-ordered, description-searchable tile order that `BlockInsertMenu` computes today moves into one helper both surfaces call.
- Admin gates on every commit: `pnpm exec vitest run --pool=forks --maxWorkers=2`, `pnpm type-check` (the build's own `vue-tsc --build`, specs included — `vue-tsc --noEmit` is not the gate), `pnpm lint`, `pnpm fmt:check`; files formatted with `pnpm exec oxfmt <files>` only; `git diff` before every commit; no AI attribution trailers; never push, never tag.
- The bridge DOM spec evaluates the bridge once per file; every test builds uniquely-id'd fixtures.

**Steps 1–4**, wherever a task says so, are the TDD cycle: write the failing test named in the task, run it and watch it fail for the stated reason, implement the minimum, run the file and the admin gates green.

## Shared contracts (named once, used by every task)

- `DragSource` gains nothing: `'palette'` already exists in `admin/src/editor/structure/coordinator.ts`; `begin('palette', { block })` and `drop()` returning `[{ type: 'InsertBlock', position, block }]` are already implemented and unit-tested.
- `InsertTarget` (TypeScript, new, `admin/src/editor/palette/target.ts`): `{ zone: DropZone; label: string }` — `zone` in the coordinator's convention (`parent`, `slot`, `index` counted against the current tree; for "after block X" that is X's own index plus one), `label` the human phrase the tab shows ("after Hero", "into Columns › col_2", "at the end of Body").
- `targetAfter(doc, id, ctx, blockTypes): InsertTarget | null` — the zone right after `id` in its own list, labelled by the block's type label; null when `id` is not in the document.
- `targetInto(doc, parent, slot, ctx, blockTypes): InsertTarget` — index 0 of an empty slot, or the end of a non-empty one, labelled "into ‹Parent label› › ‹slot›" (root: "at the end of ‹field›").
- `orderTypes(types: BlockType[], query: string): BlockType[]` (`admin/src/editor/palette/order.ts`): the active types matching `query` against label, slug and description, clustered by category (named categories alphabetical, uncategorised last) with no headings — `BlockInsertMenu`'s current rule, extracted verbatim.
- `PaletteDrag` (TypeScript, `admin/src/editor/palette/usePaletteDrag.ts`): `begin(slug, pointer)`, `move(pointer)`, `end()`, `cancel()`; owns pointer capture, the 4 px movement threshold before a session starts, the ghost element, the viewport → iframe conversion, and the `dragBegin` / `dragHover` / `dragEnd` calls; hands the page one callback per phase: `onSession(session, block)`, `onDrop(zone | null)`, `onCancel()`.
- Bridge messages, unchanged from B6.2: parent → bridge `thallo:drag-begin {session, blocks: []}`, `thallo:drag-hover {session, x, y}` (iframe viewport coordinates), `thallo:drag-legality {session, legal, reason}`, `thallo:drag-end {session}`; bridge → parent `thallo:drag-propose {session, blocks, zone}`. A parent-originated session has no wrappers to exclude (`draggedWrappers()` is empty for it), so every slot is a candidate and the coordinator alone refuses.
- `thallo:block-add-after {id}` loses its `rect`: the tab needs no anchor. `useCanvasBridge.onBlockAddAfter(cb: (id: string) => void)`.
- Blocks context (`admin/src/fields/components/blocks/context.ts`) gains `insertIntent: ((parentId: string | null, region: string | null, index: number) => void) | null` — non-null only when the field is hosted by the Design page; a gap or "Add block" click calls it instead of opening the menu when present.
- `FieldEditor` and `BlocksField` gain the prop `paletteInsert?: boolean` (default false) and the emit `insert-request: [parentId: string | null, region: string | null, index: number]`; the Design page passes `palette-insert` and listens.
- Test ids: `blocks-tab`, `palette-search`, `palette-card-<slug>`, `palette-target`, `palette-target-cancel`, `palette-ghost`; outline empty-slot rows keep `canvas-outline-slot-<parent>-<slot>` and become buttons.
