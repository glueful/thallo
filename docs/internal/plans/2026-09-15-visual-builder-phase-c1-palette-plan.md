# Visual Builder Phase C.1 — The Blocks Tab Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One palette for the Design page — a Blocks tab in the inspector that lists every active block type, inserts by click at an armed target, and drags a new block onto the stage through the coordinator — replacing the stage's add-after popover; the block list's gaps and the outline's empty slots arm that same tab.

**Architecture:** the palette is a fourth drag source for the coordinator that already exists (spec §5.1 names it: palette, outline, stage). A palette drag begins a coordinator session with `{ block }` (the factory's instance), the parent keeps the pointer through pointer capture, converts viewport coordinates to the iframe's and drives the bridge's parent-originated drag messages (`drag-begin` / `drag-hover` / `drag-end`, shipped in B6.2), the bridge answers with proposals, the coordinator judges each one with `checkInsert`, and the release asks the bridge for the authoritative final zone before the drop records one `InsertBlock`. Click insertion is the same coordinator path without a pointer session: an armed target is an insertion intent the Blocks tab remembers until a card is clicked, Escape is pressed or the selection changes, resolved to a position at the moment of use. Nothing else changes: the factory, the coordinator, the legality rules, the bridge geometry and the proofs' world all stay as B6 and B7 left them.

**Tech Stack:** Nuxt UI admin (Vue 3, vitest, Playwright for the builder proofs), the render pack's preview bridge (plain script). No PHP changes.

**Spec:** `docs/internal/superpowers/specs/2026-09-14-visual-builder-design.md` — §5.1 (the palette as a source), §5.2 (legality), §5.3 (proposals), §5.5 (insertion through the factory), §5.6 (proofs). Phase B shipped in beta.31 (`docs/internal/plans/2026-09-15-visual-builder-phase-b-plan.md`); its names are reused verbatim. This item is the first entry of OUTSTANDING section E, filed at the end of Phase B. ## Global Constraints

Every Phase B global constraint applies unchanged. The ones this plan leans on:

- **The block tree is the source of truth; the DOM supplies geometry only.** A palette drag moves nothing until its drop yields an operation; a click at an armed target is a drop with no pointer session.
- **A drop never uses a remembered proposal (review).** The bridge clears its indicator silently when the pointer leaves every slot, and a proposal can describe an earlier pointer position. So a release does not drop on the last zone the parent saw: the parent asks the bridge for the zone under the final pointer position, correlated with the session, and the bridge answers with a drop or a cancel. The parent's remembered zone drives the legality strip only.
- **A gesture is classified once (review).** A pointer gesture on a tile is either a click or a drag, decided by the movement threshold, never both; once the threshold is crossed it can never insert as a click, however late the factory answers. Every await in the gesture checks a gesture token before continuing, so a cancelled or replaced gesture cannot resurrect.
- **Whole-candidate-tree legality before any structural commit.** Every insertion — click or drop — is judged by `checkInsert(doc, position, block, ctx)` on the real factory instance, starter blocks included, immediately before it commits. Tile preflight is a cheaper, earlier check and is described honestly below: exact for allow-lists, optimistic for depth when a starter nests.
- **The builder is stricter than the API.** The Blocks tab lists every active type; whether a type may land somewhere is the destination's business. A tile the armed target refuses is not clickable and says why, and it stays draggable: click availability and drag availability are separate, because the same type may be legal elsewhere on the stage.
- **Insertion is `InsertBlock(type, starter)` from the server block factory** (§5.5). The palette never constructs a block inline; `useBlockFactory().instance(slug)` is the only source.
- **Targets carry complete identity and a freshness rule (review).** An insertion target names its root blocks field explicitly (two root fields exist in the general case; `null` parent and region do not identify one), and is resolved to a `Position` at the moment of use, never stored as an index alone: "after Hero" keeps Hero's id and re-locates it; "into Columns › col_2" recomputes the slot's end; a gap target is a position pinned to the history sequence it was armed at and is cleared by any later structural change.
- **No legacy code, no compatibility.** The stage's add-after popover, its virtual-reference anchoring, its filter and its tests leave in the same commit that arms the Blocks tab. `BlockInsertMenu.vue` stays: it is the picker of ordinary `BlocksField` editing outside the Design page and of the prose editor's in-text `/` (which inserts a split sibling carrying content), which the Design page does not replace — the same boundary Phase B drew for `BlockOutlineRail.vue`. Inside the Design page the list's gaps, its Add block button and the card header's `/` arm the tab and never open that menu.
- **One code path for ordering and filtering the types.** The category-ordered, description-searchable tile order that `BlockInsertMenu` computes today moves into one helper both surfaces call.
- Admin gates on every commit: `pnpm exec vitest run --pool=forks --maxWorkers=2`, `pnpm type-check` (the build's own `vue-tsc --build`, specs included — `vue-tsc --noEmit` is not the gate), `pnpm lint`, `pnpm fmt:check`; files formatted with `pnpm exec oxfmt <files>` only; `git diff` before every commit; no AI attribution trailers; never push, never tag.
- The bridge DOM spec evaluates the bridge once per file; every test builds uniquely-id'd fixtures.

**Steps 1–4**, wherever a task says so, are the TDD cycle: write the failing test named in the task, run it and watch it fail for the stated reason, implement the minimum, run the file and the admin gates green.

## Shared contracts (named once, used by every task)

- `DragSource` gains nothing: `'palette'` already exists in `admin/src/editor/structure/coordinator.ts`; `begin('palette', { block })` and `drop()` returning `[{ type: 'InsertBlock', position, block }]` are already implemented and unit-tested.
- `InsertTarget` (TypeScript, new, `admin/src/editor/palette/target.ts`) **(review)** — an intent, not a position:
  - `{ kind: 'after', block: string }` — after that block, wherever it now sits;
  - `{ kind: 'into', parent: string | null, field: string }` — the end of that slot (`parent === null` names a root blocks field by `field`; otherwise `field` is the parent's slot name);
  - `{ kind: 'at', position: Position, sequence: number }` — a gap, pinned to `history.currentSequence` when armed.
- `resolveTarget(target, doc, ctx, history): { position: Position; label: string } | null` — `after`: locate the block (through `createBlockListOps(ctx.regionsOf).locateById` over `ctx.blockFields()`, the walk `admin/src/editor/selection.ts` does) and return its position with index plus one, labelled by its type label ("after Hero"); null when the block is gone. `into`: index 0 of an empty slot or the list's length, labelled "into ‹Parent label› › ‹field›" or "at the end of ‹field›" for a root field; null when the parent is gone. `at`: the position as armed when `history.currentSequence === sequence`, else null. A null resolution clears the armed target and shows "That place is gone" in the strip.
- `effectiveTarget(): InsertTarget` — the armed target when one exists; else `{ kind: 'after', block: selected }` when a block is selected; else `{ kind: 'into', parent: null, field: firstBlocksField }`. Tile preflight and click insertion both use `resolveTarget(effectiveTarget())`, so the tile's answer and the click's destination can never disagree on where.
- `tilePreflight(slug, position): Legality` — `checkInsert(doc, position, { id: '', type: slug, data: {}, settings: {} }, ctx)`: exact for the slot allow-list and for a starter without children; **optimistic for depth and slot constraints when the type's starter content nests blocks**, since the placeholder is a height-one subtree and the real instance may be taller. The real instance is always revalidated before commit; a refusal there is handled like a refused drag (reason shown, target kept).
- `orderTypes(types: BlockType[], query: string): BlockType[]` (`admin/src/editor/palette/order.ts`): the active types matching `query` against label, slug and description, clustered by category (named categories alphabetical, uncategorised last) with no headings — `BlockInsertMenu`'s current rule, extracted verbatim.
- `finishDrop(zone): Promise<boolean>` **(review)** — the page's existing helper returns whether ops were applied (after `applyDrop` resolves), so a caller can select the inserted block only when it exists; today it returns `void`.
- `createPaletteDrag(deps): PaletteDrag` (`admin/src/editor/palette/usePaletteDrag.ts`) **(review)** — owns the whole gesture:
  - states `idle → pending → dragging → awaiting-drop → ended` **(review)**; `pending` on pointerdown (capture taken on the tile, origin remembered, `factory.instance(slug)` started, gesture token `++gestureId` recorded); `pending → click` when the pointer is released before the 4 px threshold (`onClick(slug)` fires exactly once, whatever the factory has done by then); `pending → dragging` when the threshold is crossed (the ghost appears at once; the coordinator session starts when the factory resolves, and every move before that is coalesced into the latest pointer position — one startup, never several); `dragging → awaiting-drop` on a release inside the iframe, entered **before** `bridge.dragDrop` is posted; `awaiting-drop → ended` on the bridge's answer or the 500 ms timeout; `dragging → ended` on a release outside the iframe, Escape, `pointercancel`, a stage reload, a factory failure (`onCancel(reason)`; a failure also toasts through `useNotify().error`), or `lostpointercapture` **while still pending or dragging** — an unexpected loss. A normal `pointerup` releases capture before the bridge's answer arrives, so `lostpointercapture` in `awaiting-drop` is expected and changes nothing.
  - after every await (`factory.instance`, the bridge's drop answer) the helper checks `gesture === gestureId && state === expected` and otherwise returns without effect: a late factory answer after a release, an Escape or a second pointerdown cannot start a session, and a late drop answer cannot insert.
  - invariant: once the threshold is crossed the gesture can never fire `onClick`; the tile's own `click` event that the browser emits after the release is suppressed once (`suppressClick`, the bridge's own device).
  - drop (review): on release inside the iframe the helper enters `awaiting-drop` and posts `bridge.dragDrop(session, x, y)` with the final pointer position converted to iframe coordinates. **The helper is the one owner of the answer**: the page's `bridge.onBlockDrop` and `bridge.onDragCancel` handlers first ask `paletteDrag.owns(session)` and, when true, hand the message to `paletteDrag.answer(zone | null)` and stop — they never call `finishDrop` for a palette session, so nothing bypasses the helper's token and timeout checks or competes with `onDrop`. `answer(zone)` in `awaiting-drop` with the current token resolves through `onDrop(zone)` (the bridge returns the fresh zone under the point; the parent judges it — see the bridge contract); `answer(null)`, a release outside the iframe, or no answer within 500 ms resolves through `onCancel`; an answer after the timeout, for an ended session or a stale token, is ignored. Either way `bridge.dragEnd(session)` follows.
  - callbacks: `onClick(slug)`, `onSession(session, block)`, `onDrop(zone)`, `onCancel(reason)`; queries: `owns(session)`.
- Bridge messages, B6.2 names plus two additions **(review)**: parent → bridge `thallo:drag-begin {session, blocks: []}`, `thallo:drag-hover {session, x, y}`, `thallo:drag-legality {session, legal, reason}`, `thallo:drag-drop {session, x, y}` (new: answer `thallo:block-drop` with the fresh zone under `x, y` **whenever one exists, whatever the session's last legality answer was** — that answer described an earlier position, and the parent's `finishDrop` judges the final zone against the current document — and `thallo:drag-cancel` only when no zone is under the point), `thallo:drag-end {session}`; bridge → parent `thallo:drag-propose {session, blocks, zone}` where `zone` may now be `null` (new: posted once when a hovered session leaves every slot, so the parent's strip and remembered zone clear with the indicator), `thallo:block-drop`, `thallo:drag-cancel`. A parent-originated session has no wrappers to exclude (`draggedWrappers()` is empty for it), so every slot is a candidate and the coordinator alone refuses. The composable validates `zone: null` as a proposal with no zone and drops anything else malformed, as today.
- `thallo:block-add-after {id}` loses its `rect`: the tab needs no anchor. `useCanvasBridge.onBlockAddAfter(cb: (id: string) => void)`.
- Blocks context (`admin/src/fields/components/blocks/context.ts`) gains `insertIntent: ((position: Position) => void) | null` **(review: a complete position, root field named)** — non-null only when the field is hosted by the Design page; a gap, the Add block button or the card header's `/` calls it instead of opening the menu when present.
- `FieldEditor` and `BlocksField` gain the prop `paletteInsert?: boolean` (default false) and the emit `insert-request: [position: Position]`; `BlocksField` builds the position from its own field name for the root list and from `{ parentId, region }` for a nested one; the Design page passes `palette-insert` and listens.
- Test ids: `blocks-tab`, `palette-search`, `palette-card-<slug>`, `palette-target`, `palette-target-cancel`, `palette-ghost`; outline empty-slot rows keep `canvas-outline-slot-<parent>-<slot>` and become buttons.
