# Admin Order Creation (Walk-In First) — Design

**Date:** 2026-08-09
**Cycle:** Orders program cycle 2. Framework OpenAPI canonicalization ships first as **v1.77.0**; engine-native draft orders then ship in `glueful/commerce` as **v1.10.0**, consumed by Thallo (complete-sale orchestration + SPA draft workspace).
**Posture:** TWO publication dependencies in strict order — framework v1.77.0, then commerce v1.10.0, each through its human-run PR/tag flow. Thallo repins after each explicit publication gate. Engine-native ownership is deliberate: cart coupling and app-owned duplicate draft models are rejected.
**Primary scenario:** in-store/walk-in purchases (POS-style). Phone/delivery orders supported; storefront checkout untouched.

---

## §1 Rulings

1. **The parked 1.6.0-candidates sketch governs**, its anti-goals affirmed: no free status dropdown, no hand-editable totals, no stock bypass. Any deliberate override (per-line price for comps/B2B) is a separate audited capability, deferred.
2. **Draft → finalize model.** Finalize is the single authority for: current prices/discounts/shipping/tax/totals; stock validation and claiming; the transition to `pending_payment`; lifecycle events and payment eligibility; idempotency and concurrent-finalization protection.
3. **Payment this cycle: mark-paid only** (cash/bank/POS via the existing guarded transition). Payvia payment links + customer emailing are ONE recorded follow-up flow, not partially added now.
4. **Walk-in identity: everything optional** — `email`, `phone`, `customer_name`, `user_uuid` all optional; a fully anonymous "Walk-in customer" is valid. Placeholder emails are never invented. Email alone never establishes ownership; phone is contact info only (never access, ownership, or an implicit account identifier); an attached `user_uuid` is the only account-history authority. No guest token is minted; guest self-access custody joins the payment-link follow-up.
5. **Explicit `fulfillment_mode`:** `in_store` (default; no addresses, `shipping_total = 0`, no method) | `delivery` (required address fields + a server-quoted shipping METHOD — never a hand-entered amount). Switching `delivery → in_store` clears the shipping selection and recalculates. Server-enforced.
6. **Complete-sale is server-orchestrated** (Thallo pack endpoint) chaining the EXISTING guarded transitions mark-paid → fulfill for finalized `in_store` orders in `pending_payment` only, returning structured per-step results; the UI never blind-retries.
7. **Isolation audit is a first-class deliverable**: drafts live in `commerce_orders`, so every existing reader is enumerated and ruled on (§2.2). Invariants: drafts excluded from storefront history, reports, payment/refund surfaces, notifications, currency locks, and ordinary order listings unless explicitly requested; drafts have no order number and claim no stock; nullable email audited across every consumer — no email means no notification attempt; abandoned drafts get explicit cancel plus bounded cleanup; origin recorded without weakening normal lifecycle events.
8. **Numbering honesty:** abandoned drafts never consume order numbers (allocation happens at finalize). Gap-free failed finalization is claimed ONLY because the allocator is being fixed and proven transactional (§2.5.9); absent that proof the spec would state the gap possibility.
9. **Digital and marketplace-partitioned lines are out of scope**: rejected at line mutation (early feedback) AND at finalize (authority). Account-attached digital admin orders and partitioned admin orders are recorded follow-ups.
10. **Riders bundled** (each its own task/commit, sequenced): storefront projection leak fix → stock NOT NULL hygiene → framework-owned OpenAPI path canonicalization + v1.77.0 publication → draft feature → commerce v1.10.0 publication → Thallo repins → ONE artifact regeneration (openapi.json + PACK_OWNED_ROUTES + SPA schema) covering cycle 1's three endpoints and cycle 2's surface.
11. All engine class/API names referenced here were mapped against v1.9.1 sources; the plan re-verifies each at implementation time.

## §2 Component contracts

### 2.1 State machine + dedicated finalize transition (engine)

- `OrderStateMachine::ALLOWED` gains `draft → [pending_payment, canceled]`; every existing pair untouched; `draft` enters no other transition.
- **`OrderRepository::transition()` REJECTS `draft → pending_payment`.** A dedicated CAS method `OrderRepository::finalizeDraftTransition()` performs that pair and is callable only by `DraftFinalizationService`, after recalculation and stock claim. No other caller can bypass the chokepoint.
- Draft cancellation (explicit or cleanup) uses `draft → canceled` via a draft-specific path that emits **draft-specific audit records only** (`draft_created`, `draft_canceled`, `draft_expired`): no customer mail, no payment/fulfillment/marketplace listeners, no ordinary order-canceled side effects.
- Cleanup: `commerce.orders.draft_ttl_days` (default **30**), bounded batches, idempotent CAS cancellation, deterministic clock injection in tests. Runs on the existing expiry cron command; explicit cancel endpoint exists regardless.

### 2.2 Isolation audit (engine + Thallo, its own task before any endpoint ships)

- Enumerate every `commerce_orders` reader in the engine AND Thallo: storefront `mine`/`show`, admin `orders.index`, Thallo search/export/payments endpoints, reports/aggregations, refunds, customer aggregation, expiry, mail listeners, webhooks, currency-lock guard, fulfillment rollups, marketplace partitioning. Each gets an explicit ruling: **exclude drafts** (default) or include-on-request (the drafts listing only).
- **Structural isolation:** centralize finalized-order predicates where possible (a shared scope/helper), then use the seeded-draft matrix as the regression ratchet.
- The matrix explicitly proves cycle-1's search/export/payments endpoints cannot **resolve** drafts by uuid — not merely that drafts are absent from default lists.
- Currency: drafts do NOT trigger the store currency lock; each draft snapshots its creation currency (the `currency` column); finalize on a changed store currency returns a typed conflict requiring cancel/recreate.
- `origin` is closed and NOT NULL (`storefront | admin`), existing rows backfilled `storefront`. `OrderPlaced` currently carries the raw order row, so this is an **additive event-payload field**, not a payload-neutral schema change: the event class and dispatch point stay unchanged, every storefront event carries `origin = storefront`, every admin finalize event carries `origin = admin`, and compatibility tests pin all pre-existing payload fields unchanged while listeners may branch on the new field.

### 2.3 Draft API (engine `AdminRouteCatalog`, manage mode, orders domain)

- `orders.drafts.store` — `POST /orders/drafts` (optional initial customer block + `fulfillment_mode`, default `in_store`).
- `orders.drafts.index` / `orders.drafts.show` — the ONLY draft-inclusive listing.
- `orders.drafts.update` — customer block (`email?`; `phone?`; `customer_name?`; `user_uuid?`), `fulfillment_mode` (switch semantics per Ruling 5), addresses, shipping METHOD id (`delivery` only; re-quoted, never an amount), discount code (validated, not consumed until finalize). **Phone request contract:** `phone` is a nullable scalar string in international form. Trim it, cap the display input at 32 characters, require a leading `+`, remove only ASCII spaces, `-`, `(` and `)` for canonicalization, then require `\A\+[1-9][0-9]{7,14}\z`; store the canonical value in `phone_normalized` and the trimmed operator input in `phone_display`. `null` or an empty trimmed string clears both columns atomically; every other invalid form is 422. Phone is never used as an identity lookup.
- **User attachment:** `user_uuid` must resolve to an active user via the user provider. Unknown or inactive UUIDs are **422 validation errors** with the same closed public message; if `email` is ALSO supplied and mismatches the resolved user's email, the update is a **409 typed conflict** — never silently linked. The engine endpoint accepts a known uuid under its existing order-manage authority and does not expose a search surface. Thallo's optional picker uses the existing `GET /v1/users` only when `users.user_lookup.enabled`, `users.user_lookup.list.enabled`, AND effective `users.view` are all true (the route registers only under both config keys — the flag must reflect real endpoint availability); `CommerceMetaController` publishes the resulting closed `can_attach_user` flag. When false, the SPA omits the picker and makes no users request; walk-in fields remain fully functional.
- `orders.drafts.lines.store|update|destroy` — stable line UUIDs in `commerce_order_lines`; each mutation re-resolves through the **shared purchasable-line resolver** (§2.4) and stores an advisory snapshot; digital or marketplace-partitioned items ⇒ typed rejection at mutation time.
- `orders.drafts.recalculate` — **the explicit drift-acceptance operation**: refreshes advisory line snapshots to current catalog values, recalculates totals (pricing, discount preview, tax, shipping re-quote), and CAS-increments `draft_revision`. This is how a price-drift finalize conflict is cleared.
- `orders.drafts.finalize` — §2.5. `orders.drafts.cancel` — draft-specific event only.
- **Revision custody:** every customer/line/shipping mutation CAS-increments `draft_revision`; finalize accepts the expected revision and refuses stale state (typed conflict → reload).
- **Eligibility surface (one path):** the engine's admin product search projection exposes authoritative `admin_draft_eligible: bool` + nullable closed `admin_draft_ineligible_reason` (`digital | marketplace | unavailable`). The SPA uses those fields to disable ineligible results before mutation; the line endpoint independently rechecks and returns the same closed reason as the write authority. No client reconstruction and no line-endpoint-as-discovery fallback.

### 2.4 Shared purchasable-line resolver (engine refactor)

One extracted resolver owns the shared product/variant availability, live variant price, option-value derivation, shipping/tax attachment, and digital/marketplace classification used by BOTH storefront checkout and drafts. It exposes two explicit addon policies rather than one ambiguous array contract:

- `resolvePersistedSnapshot(...)` is the storefront/cart path. It prices the already-persisted canonical addon snapshot exactly as `CartService::pricedLines()` does today; addon-definition edits never reprice an existing cart line.
- `resolveSelections(...)` is the draft mutation/recalculate/finalize path. It resolves raw selections (or selections reconstructed from the draft's advisory snapshot) against current active addon definitions and returns a fresh canonical snapshot, allowing finalize to report addon/price drift.

Caller-supplied option values are never authoritative; both methods derive them from the resolved variant. The methods share one private base resolution path, and checkout behavior remains byte-identical. Two separate repository pipelines, or a single untyped `addons/options` argument whose meaning changes by caller, are expressly insufficient.

### 2.5 `DraftFinalizationService::finalize()` — tenant-safe preflight + one transaction

Before opening the transaction, perform a **read-only tenant-scoped order lookup**. Unknown and cross-tenant UUIDs return the same non-revealing 404 with **zero attempt-ledger writes**. This preflight is containment only, not authority; the row and every mutable invariant are re-read under lock in the transaction.

1. The controller requires `X-Idempotency-Key` matching `\A[A-Za-z0-9._:-]{16,191}\z` and a non-negative integer `expected_revision`; malformed/missing input returns 422 before lookup or ledger access. Load the tenant-scoped order `FOR UPDATE` (or the driver's equivalent), then claim/replay `commerce_order_draft_attempts` **before any stock or business mutation**. The fingerprint is SHA-256 over canonical `{order_uuid, expected_revision}`. Same key + same fingerprint + completed attempt ⇒ return that finalized order with no re-execution; same key + different fingerprint ⇒ 409. A fresh claim remains in this transaction, so every later failure rolls it back. The order lock serializes different keys for the same draft; only one can finalize.
2. For a fresh claim, verify `draft` status + expected `draft_revision` + currency snapshot vs store currency (each mismatch a distinct typed conflict). Replay is resolved before these checks so the original revision remains replayable after finalization.
3. Re-resolve every line through `resolveSelections()` using selections reconstructed from its advisory snapshot (availability, current variant price, current addon definitions); recheck digital/marketplace exclusions; drift ⇒ typed per-line conflict list, abort, draft untouched. Storefront checkout continues to use `resolvePersistedSnapshot()` and does not inherit this drift policy.
4. Recalculate all totals server-side; stored advisory totals discarded.
5. Claim stock per tracked line via `StockRepository::decrement()` (atomic); failure ⇒ typed per-line stock conflict, rollback.
6. Allocate `order_number` via the FIXED `OrderNumberGenerator` (savepoint-isolated retry — the current catch-without-savepoint can poison a PostgreSQL transaction; a two-concurrent-finalizers first-order test is the precondition for claiming transactional numbering).
7. Atomically replace advisory line snapshots with authoritative snapshots (same stable line UUIDs — no duplicate insertion), write totals + `placed_at`, record stock movements, consume discount. Anonymous discount identity: ordinary discounts use the draft/order UUID; `once_per_buyer` without user/email ⇒ 422 at application AND finalize.
8. Dedicated CAS `draft → pending_payment`; mark the attempt `completed`; `finalized` audit row INSIDE the transaction. The attempt claim, order mutation, and attempt completion commit atomically.
9. **`OrderPlaced` dispatches only after commit** (matching `CheckoutService.php:231` semantics): rollback ⇒ zero dispatch; fresh finalize ⇒ exactly one; idempotent replay ⇒ no redispatch. Mail listener consults `origin` + email presence: no email ⇒ short-circuit before the mailer; the `commerce.order_confirmation` toggle governs admin-origin sends.
10. Failure at any step: rollback leaves an editable `draft` with zero stock/event/transition side effects.

### 2.6 Schema (engine v1.10.0 migrations)

- `commerce_orders`: `order_number` nullable — the EXISTING `(tenant_uuid, order_number)` unique index is retained (SQLite and PostgreSQL both permit multiple NULLs while rejecting duplicate non-null values; tested on both); `email` nullable; `guest_token_hash` nullable (anonymous admin orders mint no credential; access tests prove null grants no guest access); new: `phone_normalized` (nullable, canonical strict E.164), `phone_display` (nullable, max 32-character trimmed operator input), `customer_name` (nullable), `origin` (NOT NULL, `storefront|admin`, backfill `storefront`), `fulfillment_mode` (NOT NULL, `in_store|delivery`, backfill `delivery` — documented as conservative compatibility meaning "not eligible for automatic in-store completion," not a claim that historical orders shipped), `draft_revision` (int NOT NULL default 0).
- New table `commerce_order_draft_attempts` (engine-owned; `CheckoutAttemptAuthority` is NOT reused — it is a host seam whose completion shape requires an order reference and raw guest credential): `id` auto-increment bigint PK; `tenant_uuid` varchar(12); `idempotency_key` varchar(191); `request_fingerprint` char/varchar(64); `order_uuid` varchar(12) (the draft and finalized order are the same row/uuid); `status` closed `pending|completed`; nullable `completed_at`; `created_at` and `updated_at`. Unique `(tenant_uuid, idempotency_key)` is the sole key authority. The first-use insert runs in a savepoint and catches a unique violation outside it, then re-reads and verifies the winner row; unrelated insert failures rethrow. This keeps PostgreSQL's outer transaction usable and makes the same key across different drafts deterministically produce a fingerprint conflict instead of a driver error. Different keys for one draft are serialized by the locked order row and losing transactions roll their pending attempt back. No separate `draft_uuid`, no generic `key` column, no guest credential, and no fields are projected outside the repository. Registered in tenant purge/adoption inventory.
- Rider: `commerce_stock.quantity NULL → 0`, `tracked NULL → false` backfill, then NOT NULL — preserving current runtime behavior; both drivers.
- **Projection/PII ratchet:** `customer_name`/`phone_*`/`draft_revision`/attempt internals absent from storefront/public projections by default; the ordinary admin order projection explicitly adds `customer_name`, `phone_normalized`, `phone_display`, `fulfillment_mode`, and `origin` so finalized walk-in orders remain operable, while the draft projection additionally carries `draft_revision`; attempt fields never leave their repository. Thallo treats admin-order email as nullable across list, detail, invoice, copy controls, and types — no empty-string placeholder.
- **Migration gates:** fresh install AND real v1.9.1 upgrade, SQLite + PostgreSQL: multiple null order numbers, nullable email/token, backfills, tenant purge/adoption, rollback safety.

### 2.7 Riders (engine, sequenced before the draft work where noted)

1. Storefront wire-projection leak fix (first): `accessCheckedOrder()` remains the raw INTERNAL access-checked row because downloads and payment retry require internal fields. The closed projection is applied only at HTTP order-response boundaries after `authorizedOrder()` enrichment, and to each `mine()` item.
2. Stock NOT NULL migration (second).
3. OpenAPI path canonicalization belongs to `glueful/framework`'s `OpenApiGenerator`/`DocGenerator`, ships as v1.77.0, and lands before any artifact generation. Commerce has no generator and owns no part of this rider.
4. **`OrderFulfillmentService` extraction**: non-partitioned fulfillment logic moves out of `AdminOrderController::fulfill()` into a service peer of `OrderPaymentService::markPaid()`. The service accepts the existing nullable `tracking_ref`, owns the transaction, raw-order reload, and exactly-once `OrderFulfilled` dispatch; the controller retains marketplace fan-out and HTTP projection. The controller AND Thallo's complete-sale coordinator delegate. The pack never reproduces controller transaction/event logic.

### 2.8 Thallo: complete-sale + allowlist

- Allowlist gains the `orders.drafts.*` keys; mount-parity fixture regenerated.
- `POST /v1/admin/commerce/orders/{uuid}/complete-sale` (`commerce.manage`): resolve tenant-scoped order FIRST — unknown/cross-tenant ⇒ **404**; wrong status, non-`in_store`, or concurrent transition ⇒ **409**; malformed input ⇒ **422**. Chains `OrderPaymentService::markPaid()` then `OrderFulfillmentService` with per-step CAS/audit/events intact. Every success/error reload is serialized through the engine's closed `OrderProjection::forAdmin()`; raw tenant/token/revision/attempt fields never cross this pack response. Response contract:
  - mark-paid **domain conflict** ⇒ 409, mark-paid `failed`, fulfill `skipped`, refreshed order;
  - unexpected mark-paid exception ⇒ log it, reload the order, return a sanitized 500, and **never continue to fulfillment after the throw**. If the reload is still pending, mark-paid is `failed`; if the payment transaction committed before an after-commit callback threw and the reload is paid, mark-paid is truthfully `done`. Fulfill is `skipped` in both cases and the ordinary guarded Fulfill action is the recovery path for the latter;
  - mark-paid committed, fulfillment domain conflict ⇒ 409 with the refreshed PAID order + structured steps;
  - unexpected fulfillment failure ⇒ logged 500 with sanitized step error + refreshed paid order;
  - exception messages never exposed directly.
  - After partial completion, the normal guarded Fulfill action is the recovery path; Complete sale is never blindly retried.
- Concurrency: two simultaneous complete-sale calls ⇒ exactly one paid event and one fulfilled event; the loser receives a truthful conflict + current order, never duplicate side effects.

### 2.9 SPA (admin/)

- "Create order" (gated `can_manage`) → `/commerce/orders/create?draft={uuid}` draft workspace: absent `draft` creates exactly one row and immediately replaces the URL with its UUID; present `draft` loads that row. Refresh and the drafts-list Resume action therefore reopen the same draft. Finalize/cancel clears local custody before navigation. The workspace includes a product line picker driven by the engine's `admin_draft_eligible` + reason codes (never client-inferred); qty/addons; all-optional customer block; fulfillment-mode toggle (in_store default; delivery reveals addresses + quoted shipping methods); server `recalculate` with advisory totals badge; discount code entry. Account attachment is an optional enhancement gated by `CommerceMetaController.can_attach_user`: true uses the existing users query; false renders no picker, sends no lookup request, and does not impede an anonymous walk-in sale.
- Finalize success → standard order detail. The client sends a `crypto.randomUUID()` idempotency key in `X-Idempotency-Key`: one key per `(draft_uuid, expected_revision)`, retained in `sessionStorage` across reloads and ambiguous network failures, reused until a definitive response, rotated only when `draft_revision` changes, and cleared after confirmed finalize/cancel. The stored value is opaque and contains no customer/order data. Conflict renderings: per-line drift (with "Refresh prices" invoking `recalculate`), stock, revision (reload), currency (cancel/recreate), idempotency 409.
- Order detail: finalized `in_store` + `pending_payment` ⇒ primary **Complete sale** action rendering per-step results and the true partial-failure state (paid-but-unfulfilled resumes via the standard Fulfill).
- Drafts view (filtered listing) with resume/cancel; the cycle-1 orders list/search stays draft-blind.

## §3 Test matrix (distributed to plan tasks)

**Engine:** state-machine table incl. `transition()` rejecting `draft → pending_payment`; dedicated finalize CAS; finalize matrix — unknown/cross-tenant uuid produces 404 and zero attempt rows, same key+fingerprint replay / same key+different fingerprint / concurrent keys, revision staleness, currency conflict, per-line drift/stock/digital/marketplace conflicts, discount identity (ordinary via uuid; `once_per_buyer` 422), rollback removes the pending attempt and leaves an editable draft with zero side effects, after-commit dispatch triple (rollback ⇒ none; fresh ⇒ once; replay ⇒ none); exact attempt-table shape + tenant/key uniqueness on SQLite/PostgreSQL, including concurrent same-key claims for different drafts with a usable outer transaction; two-concurrent-finalizers order-number test (savepoint fix precondition); shared base-resolution parity plus explicit addon-policy tests proving checkout preserves persisted snapshots while drafts re-resolve current definitions; admin product eligibility projection and write-side reason parity; phone normalization/clearing/rejection matrix; unknown/inactive user 422 + supplied-email mismatch 409; additive `OrderPlaced.origin` compatibility; isolation-audit seeded-draft matrix (every §2.2 reader + cycle-1 endpoints cannot resolve drafts by uuid); draft cleanup (TTL 30, bounded batches, idempotent CAS, deterministic clock); migration gates (§2.6); rider regressions (projection closed-field test; stock backfill); `OrderFulfillmentService` parity with the previous controller behavior; null `guest_token_hash` grants no guest access; no-email guard across placed/paid/fulfilled/refund/notifying-note listeners.
**Pack:** complete-sale truth table (404/409/422 discipline; mark-paid domain conflict; unexpected mark-paid before commit; unexpected mark-paid after commit with truthful paid reload; fulfillment domain conflict; unexpected fulfillment failure; concurrency single-winner); `CommerceMetaController.can_attach_user` matrix (`users.view` × list-enabled); allowlist/mount parity.

## §4 Follow-ups (recorded, out of scope)

- Payvia payment links + customer emailing for admin orders (one flow: link custody, expiry, guest access, delivery).
- Guest self-service access custody for admin-born orders.
- Account-attached digital admin orders (download delivery defined by account custody).
- Marketplace-partitioned admin orders (seller-order split + ledger at finalize).
- Audited per-line price override capability (comps/B2B).
- Retire Thallo's temporary orders search/export at upstream filter parity (carried from cycle 1).
