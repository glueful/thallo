# Payment Links for Admin Orders — Design

**Date:** 2026-08-11
**Cycle:** Orders program cycle 3 — the "Payvia payment links + customer emailing" follow-up from the admin-order-creation cycle.
**Posture:** THREE-release train, strict order: **Payvia 2.6.0** (ensure-live session semantics) → **Commerce 1.11.0** (payment-link machinery) → **Thallo** (landing page, admin controls, email, SPA). Each upstream release is human-run (push dev, PR dev→main, merge, tag, Packagist) behind an explicit publication gate; no path-repo/vendor-edit workarounds.
**Primary scenario:** phone/remote orders — admin finalizes a walk-in/delivery order, sends the customer a durable payment link; the customer pays through the hosted gateway page; webhooks settle. The in-store complete-sale path is untouched.

---

## §1 Rulings

1. **The link is an app landing page, never a raw gateway URL.** `/checkout/pay/{token}` identifies a revocable payment-link record; the Pay action ensures a live gateway session server-side. Gateway URLs/references stay server-controlled until that redirect, webhooks remain the settlement authority, and the landing page only displays current state. Revoking the APP link prevents future use of that token; it cannot recall a hosted gateway URL already handed to a browser. Provider-session exposure is therefore tracked separately and governed by Ruling 3.
2. **Token custody:** ≥256-bit random, presented as exactly **64 lowercase hex characters**; stored HASHED only (SHA-256); tenant/order-bound; purpose-bound to payment (never a guest credential — no order history, downloads, address edits, cancellation, refunds, notes, or account ownership); revocable; expiring; excluded from application-side plaintext persistence (databases, queues, logs, audit rows — the recipient's mailbox necessarily contains the link). Raw token egress: the mint/regenerate response's one-time surface, and the send-time email body. Nothing else — not order events, not projections, not status reads.
3. **Link TTL is an explicit stock-reservation lease, with a fail-closed provider-session boundary.** Default `commerce.payment_links.ttl_days` = 7, operator-configurable clamped 1–30. While an admin-origin `pending_payment` order holds an ACTIVE unexpired link, the ordinary 60-minute expiry sweep skips it. If NO hosted session URL has ever been returned for the order, expiry/revocation returns it to the next ordinary sweep. Once a hosted URL has been returned, link expiry/revocation still blocks the app token but automatic stock release/cancellation stays blocked: Paystack cannot invalidate or prove that previously-issued session dead, and Commerce's late-payment path does not refund a provider charge. The operator must mark paid or explicitly cancel with an `accept_late_payment_risk` acknowledgement; that guarded cancellation records an audit event and warns that a later provider charge requires refund handling. This conservative rule applies uniformly in v1; provider-confirmed session invalidation is a follow-up optimization. Storefront orders remain unchanged. Paid/canceled orders make every link immediately unusable. Sweep and payment initiation recheck link/order state transactionally (the candidate-query filter is a prefilter only). Admin UI distinguishes "Stock reserved until …" from "Payment session may still be live; stock remains reserved until this order is resolved."
4. **Delivery = copy + email; the page is pay-only.** Copy always available; email only when the order has a valid email address, the rich email channel is available, AND the `payment_request` template toggle (default **OFF**) is on. Send is an explicit admin action — mint never auto-sends. Missing email infrastructure disables Send with a reason; Copy remains available and the pack never fails to boot.
5. **Ensure-live, never force-fresh.** Payvia's `initiate()` ensures ONE provably live hosted session per payable: no intent ⇒ create; confirmed-live ⇒ same URL; confirmed-dead ⇒ renew; unknown provider state ⇒ fail closed, never replace. Commerce never requests an unconditional fresh session. This is a Payvia-only change (the existing contract permits returning/refreshing the same logical intent) — no contracts-package release.
6. **Paystack renewal is unavailable in 2.6.0.** A new initialization does not prove the old authorization URL dead, and a late second settlement is only detected after a double charge. Renewal requires provider-confirmed permanent death; no timeout guessing. UI/docs must not imply link regeneration renews or invalidates an indeterminate Paystack session — the merchant's recovery is offline completion (mark-paid) or explicit risk-acknowledged cancellation/recreation.
7. **One active link per order**, enforced transactionally (not by index): mint locks the tenant-owned order, revokes the current active link, inserts the replacement — one transaction. Mint, revoke, initiate, and expiry all use the same order-before-link lock order.
8. **Hash-only custody defines the admin flows:** Create/Regenerate return the raw URL once; while visible, "Send this link" is offered; after it's gone, "Regenerate and send" (with confirmation that the previous link becomes invalid). There is no encrypted-retrieval path.
9. **URL composition lives in Thallo, behind an engine host seam.** Commerce's `mintPublic()` passes its newly generated token in memory to `PaymentLinkPublicUrlProvider::urlFor(context, rawToken)` before persistence and returns only that provider's validated absolute HTTPS URL. Thallo binds the provider and composes `/checkout/pay/{token}` via `ShopUrlGenerator::paymentLink()` plus `CanonicalPublicOriginResolver` — never the request Host. This preserves one API owner: Commerce's catalog controller owns mint/revoke/status; Thallo does not shadow those routes and owns only send. Gateway return/cancel URLs NEVER contain the token: payment-link checkout uses a separate signed, non-authorizing return handle that can render only a generic submitted/canceled receipt. The existing order return route is not reused because it requires `GuestOrderCookie`, which a pay-only visitor deliberately never receives.
10. **Engine-native ownership** (Commerce 1.11.0): link record, token custody, TTL/lease semantics, expiry integration, initiation rules, terminal behavior. Thallo owns only its application surfaces (route/page, admin controls, email template + toggle, allowlist/SPA, artifacts).

## §2 Component contracts

### 2.1 Payvia 2.6.0 — ensure-live sessions (repo: extensions/payvia)

- **`PayviaPaymentCollector::initiate()` becomes ensure-live** (Ruling 5). Backed by **reference-addressable session attempts**:
  - **New-row supersession:** renewal preserves the old intent row as `superseded` (its provider reference remains webhook-addressable), inserts a new open attempt; exactly one OPEN attempt per payable; concurrent renewal calls serialize (payable-scoped locking).
  - **Per-durable-attempt idempotency:** an attempt UUID is claimed BEFORE provider I/O and reused across timeouts/crashes — Stripe's idempotency key and Paystack's reference derive from it. A retry of one renewal returns the same provider session; a later confirmed renewal claims a new attempt UUID. (Fixes the fixed per-payable Stripe key at `StripeGateway.php:148`.)
  - **Stripe renewal:** status → expire → re-fetch; only `confirmed_dead` permits supersession. `completed`, still-open, transport failure, or unparseable state never frees the old intent.
  - **Paystack:** create + confirmed-live reuse only; expired-without-proof/unknown ⇒ typed failure; renewal unavailable (Ruling 6).
- **Migration of `payment_intents` is part of 2.6.0, not plan-time inference.** Existing rows remain valid. `reference` becomes nullable so an `initializing` row can be claimed before provider I/O; status is a service-enforced closed set `initializing|open|superseded|closed|failed`; the existing `(tenant_uuid, idempotency_key)` unique port is retained, with `initializing` and `open` sharing the payable's active key and every terminal/superseded row re-keyed by attempt UUID; `(tenant_uuid, gateway, reference)` is unique once reference is non-null. A transport timeout/unknown outcome leaves the row `initializing` and retries the SAME attempt UUID/provider idempotency key. Only a classified deterministic provider rejection marks `failed` and frees the active port. Fresh-install and real-upgrade fixtures run on SQLite and PostgreSQL, including multiple nullable references, duplicate-reference rejection, and an initializing-row crash/retry.
- **`ConfirmationDispatcher` becomes reference-aware:** resolves and closes the exact `(tenant, gateway, provider reference)` intent row — never "whichever is open for the payable" (`ConfirmationDispatcher.php:37`). A webhook for a superseded attempt attributes to that attempt; settlement of a superseded session against an already-paid payable is refused by the existing order CAS (fixture-proven on real supersession paths — Stripe).
- **Hosted redirect URLs are a Payvia trust boundary.** Each built-in driver accepts only an absolute HTTPS URL whose host exactly matches its configured `checkout_hosts` set: `payvia.gateways.stripe.checkout_hosts` defaults to `['checkout.stripe.com']`; `payvia.gateways.paystack.checkout_hosts` defaults to `['checkout.paystack.com']`. Matching is case-normalized but otherwise exact; userinfo, explicit ports, trailing-dot/subdomain lookalikes, HTTP, missing hosts, and malformed URLs are rejected. Paystack's currently unchecked `authorization_url` is fixed here. Missing/malformed/untrusted URLs never enter an intent payload as usable checkout URLs. Thallo independently repeats the absolute-HTTPS check before emitting `Location`.
- Provider matrix (fixtures): Stripe — create / confirmed-live / confirmed-dead renewal / unknown-fails-closed; Paystack — create / confirmed-live reuse / unknown-or-expired-without-proof fails closed, renewal unavailable. Double-settlement tests apply to actual supersession paths only.

### 2.2 Commerce 1.11.0 — the payment-link machinery (repo: extensions/commerce)

- **Table `commerce_payment_links`:** `id` PK autoincrement; `uuid` vc12; `tenant_uuid` vc12; `order_uuid` vc12; `token_hash` vc64; `status` closed `active|revoked|expired|consumed`; `expires_at` NOT NULL; `created_by` vc12; `consumed_at`/`revoked_at` nullable; `initiation_window_started_at` nullable; `initiation_count` int NOT NULL default 0; `provider_session_issued_at` nullable; timestamps. Unique `(tenant_uuid, token_hash)`; index `(tenant_uuid, order_uuid, status)` plus the issued-session lookup used by expiry/cancel guards. Tenant purge/adoption registered. The transactional one-active authority is Ruling 7 — the index is not the enforcement mechanism. The rate window is a fixed UTC one-hour window, reset atomically under the link lock; `commerce.payment_links.initiations_per_hour` defaults to 10 and clamps 1–100; tests inject a deterministic clock.
- **`PaymentLinkService`:**
  - `mint(context, tenant, orderUuid, ttlDays, actorUuid): {rawToken, link}` — only for tenant-owned `origin='admin'` `status='pending_payment'` orders (else typed conflict); TTL clamped 1–30 (default from config); one transaction per Ruling 7; the raw token appears in this return value and nowhere else engine-side.
  - `mintPublic(context, tenant, orderUuid, ttlDays, actorUuid): {url,link}` — the controller/send-safe form. It generates the token, asks the bound `PaymentLinkPublicUrlProvider` to compose the URL, and validates that URL BEFORE opening the mint transaction; only then does it persist the token hash through the same private mint operation. Missing/invalid provider therefore creates no link. The returned URL contains the token, but no separate raw-token field.
  - `revoke(context, tenant, orderUuid, actorUuid): void`.
  - `resolveByToken(context, rawToken): ?LinkView` — shape-gate (64 lowercase hex) before any lookup; hash and query under the host-resolved tenant; unknown/malformed/cross-tenant are indistinguishable (one generic null ⇒ 404). Engine `LinkView` contains ONLY order reference (number), line names/quantities, totals, currency, payment/link state, `expires_at`, and the provider-session-exposure flag. Thallo's page view adds store identity from its own settings authority. EXCLUDED engine-side: store identity, email, phone, addresses, user uuid, notes, internal ids, token, token_hash.
  - `matchCurrentToken(context, tenant, orderUuid, rawToken): ?PaymentLinkAdminView` — authenticated-host seam for `mode=current`: shape-gates and hashes the submitted token, locks order then current link, and returns a closed admin view (`link_uuid`, state, expiry, provider-session-exposure flag) only when it is the order's CURRENT active link. Missing/cross-tenant orders remain 404 at the controller boundary; a well-owned order whose submitted token is stale/wrong becomes 409 `payment_link_changed`. Thallo never reads the link table directly.
  - New Commerce-owned host seam `PaymentLinkPublicUrlProvider::urlFor(context, rawToken): ?string`. Commerce binds a default unavailable implementation so hosts without a public payment-link surface still compile and fail explicitly; Thallo overrides it. `mintPublic()` passes the newly generated token to it in memory before persistence. Commerce requires an absolute HTTPS URL with no userinfo, port, query, or fragment and with the raw token appearing exactly once as the final path segment. Missing/invalid binding is typed unavailable and mint does not occur. Thallo's implementation uses its canonical-origin and shop-URL authorities. This is the single mint/revoke/status route path; no pack proxy shadows it.
  - New Commerce-owned host seam `PaymentLinkReturnUrlProvider::urlsFor(context, linkUuid): ?{return:string,cancel:string}`. It receives link UUID only — NEVER the raw token — and Commerce validates both outputs as absolute HTTPS before placing them in `PayableReference` metadata. Thallo binds it to canonical-origin signed return/cancel routes (§2.3). Missing/invalid binding is a typed unavailable outcome for payment-link initiation, not fallback to the guest-cookie order return route or a gateway-global callback.
  - `initiateByToken(context, rawToken): {checkoutUrl}` (idempotency is Payvia's per-durable-attempt mechanism — no caller-supplied key; repeated clicks converge on the one live session) is explicitly **two-phase; no provider/network call runs inside a database transaction or while row locks are held**. Phase A transaction locks order then link, revalidates link `active` + unexpired + order `pending_payment`, atomically claims the fixed-window counter BEFORE provider I/O, captures the link/order identity, and commits. Outside the transaction it constructs the ordinary `commerce_order` PayableReference from the live order plus `PaymentLinkReturnUrlProvider` metadata, then calls Payvia ensure-live. Phase B locks the same order then link UUID, rechecks every predicate, validates `status='ok'` plus the checkout URL, stamps `provider_session_issued_at` before returning it, and commits. A concurrent revoke/cancel makes Phase B refuse the redirect; an attempt created during that race remains server-side and no URL is exposed. Payvia `manual`, missing URL, malformed/untrusted URL, missing/invalid return URLs, and renewal-unavailable outcomes become typed unavailable states, never empty/open redirects or exception leaks.
  - Terminal transitions: order paid ⇒ link `consumed` (eagerly where OrderPaid is observed; lazily on resolve); canceled/refunded order ⇒ resolve returns honest state; TTL passed ⇒ `expired` lazily on resolve + swept.
- **Expiry/cancel integration:** one shared `PaymentSessionExposureGuard` is the authority for every non-draft cancellation path (currently `ExpiryService` and `AdminOrderController`; an inventory test pins that set). `ExpiryService` candidate query adds prefilters for active-unexpired links AND any historical link with `provider_session_issued_at IS NOT NULL`; INSIDE each per-order transaction it locks/reloads the order and invokes the guard before releasing stock or transitioning (closes mint-vs-sweep and initiate-vs-sweep races; prefilters are never authority). An uninitiated expired/revoked link returns the order to the ordinary sweep. An initiated link blocks automatic cancellation regardless of link status until payment or an explicit operator cancellation carrying `accept_late_payment_risk=true`; the latter records `payment_session_risk_accepted` with actor/time in the same cancellation transaction before stock release. The ordinary admin cancel endpoint uses the same guard so it cannot bypass this policy; future final-order cancellation authorities fail the inventory test until wired.
- Catalog entries (manage mode): `orders.payment_link.store|destroy|show`. Store calls `mintPublic()` and returns its one-time URL; `show` returns state/expiry/exposure only — never token or hash. Thallo mounts these entries through its normal allowlist and does not redeclare their method/path pairs.

### 2.3 Thallo — public landing + initiation

- `GET /checkout/pay/{token}` (shop-routes, reserved-path guarded, never page-cached): shape-gate before lookup; render the LinkView states — active ⇒ summary + Pay form; paid ⇒ thank-you; revoked/expired/canceled ⇒ honest "no longer valid — contact the merchant". Headers on ALL responses: `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex, nofollow, noarchive`. Zero third-party assets. Generic 404 for unknown/malformed/cross-tenant.
- `POST /checkout/pay/{token}/initiate`: **ShopCsrfGuard** (established anonymous-checkout-POST policy) + Thallo IP rate limit + the engine per-link counter; a **no-JS form POST** answering **303** only after an independent final absolute-HTTPS URL check; same headers repeated on the POST response. Manual/unconfigured gateway, unavailable email-independent payment capability, missing URL, provider uncertainty, or a Phase-B race renders an honest no-store unavailable state and never emits `Location`.
- `GET /checkout/pay/return/{linkUuid}/{signature}` and `/checkout/pay/cancel/{linkUuid}/{signature}` are canonical-origin URLs supplied through `PaymentLinkReturnUrlProvider`. `PaymentLinkReturnSigner` derives the configured `app.key` with the SAME `base64:` decoding/fail-closed discipline as `ResolvesPreviewKey`, signs the route purpose + link UUID with distinct `payment-link-return` / `payment-link-cancel` purposes, and verifies with `hash_equals()` before trusting either value. No fallback/default key. The handle grants NO payment initiation and reveals NO order/link fields: it renders only a generic no-store/no-referrer/noindex "payment submitted; confirmation may take a moment" or "payment canceled; reopen the original link to retry" receipt. Invalid signature/shape ⇒ the same generic 404. Provider payloads/intents may persist this non-authorizing handle; they never receive the raw payment token. The existing `/checkout/return/{orderNumber}` + guest-cookie confirmation flow stays byte-identical.
- Log-redaction guidance for the token path segment documented (app + reverse-proxy examples).
- `ShopUrlGenerator::paymentLink(rawToken)` composes the path; absolute URLs via `CanonicalPublicOriginResolver` (Ruling 9).

### 2.4 Thallo — admin surfaces

- Commerce's mounted catalog endpoints own mint/revoke/status; Thallo binds `PaymentLinkPublicUrlProvider` to compose their mint response. The pack owns only **send** (`POST /orders/{uuid}/payment-link/send`) with required `Idempotency-Key`, validated as an opaque 16–128-character value. `mode=current` is available only while the one-time URL is visible: the authenticated request submits the raw token back, and the controller delegates to `PaymentLinkService::matchCurrentToken()` — never a pack query or reconstructed predicate. Missing/cross-tenant order ⇒ 404; stale/wrong token for an owned order ⇒ 409 `payment_link_changed`. The token is never logged/persisted. `mode=regenerate` accepts TTL but no token, claims delivery idempotency first, then calls `mintPublic()` and sends its URL in one request; confirmation states that the old link is invalidated. On delivery failure the new link STAYS active and its URL returns on the ORIGINAL response for manual copy.
- **Pack table `thallo_commerce_payment_link_deliveries`:** `id`, `uuid`, `tenant_uuid`, unique `(tenant_uuid,idempotency_key)`, `idempotency_key`, `fingerprint`, `order_uuid`, nullable `link_uuid` until mint completes, `recipient_hash`, mode `current|regenerate`, status `processing|sent|failed|indeterminate`, safe `error_code`, optional provider message id, timestamps. Tenant purge/adoption registered. Same key+fingerprint replays the recorded outcome WITHOUT a raw URL or another send; same key+different fingerprint ⇒ 409. `thallo-commerce.payment_links.delivery_processing_stale_seconds` defaults to 300 and clamps 60–3600; once that deterministic-clock threshold passes, a crashed `processing` attempt becomes `indeterminate`. Because plaintext is not recoverable, replay never regenerates silently and instructs the operator to use a new key/regenerate. Receipts never contain token, email address, rendered subject/body, or transport exception text. Fresh-install and real-upgrade migration fixtures run on SQLite and PostgreSQL, with tenant purge/adoption coverage.
- **`PaymentRequestMailer` (dedicated, synchronous):** resolves the registered `email` channel through the framework channel registry and requires `RichNotificationChannel`; it calls that channel directly (the template test-send pattern), never hard-types the optional email extension in the pack contract. Never `NotificationService::send()` (which persists the full payload — would store the raw token, `NotificationService.php:164`). Delivery failure returns a typed safe result; never auto-queued. Missing/unavailable rich email channel is an explicit `email_available=false` meta state and a send refusal, never a boot failure.
- Email template `payment_request`: `EmailSettingsController::TEMPLATES` + `CommerceEmailTemplates` definition (editable; placeholder chips incl. expiry date; the link uses the EXISTING validated **`action_url`** placeholder — no new URL placeholder); `packages/thallo-commerce/config/thallo-commerce.php` explicitly sets `email.payment_request.enabled=false` (the controller's generic fallback is true, so omission is forbidden); substitution at send time only (stored template never contains a token). `CommerceMetaController` always emits `email_available`, computed through the same rich-channel availability authority the mailer uses — this field is not conditional on SPA implementation preference.
- SPA order-detail "Payment link" card (`origin='admin'` + `pending_payment`): Create (TTL input within clamp), one-time copy surface, "Stock reserved until …", Regenerate, Revoke, Send (visible only when order email present + toggle on + rich email channel available; disabled-with-reason otherwise). After provider URL exposure, expiry/revoke copy changes to the provider-session warning from Ruling 3 and cancellation requires the explicit risk acknowledgement. Paystack honesty: the card never claims regeneration revives or invalidates a dead/unknown gateway session; the documented recovery is mark-paid (offline) or risk-acknowledged cancel/recreate. Complete-sale untouched; drafts have no link surface.

## §3 Test matrix

**Payvia:** the §2.1 provider matrix; the explicit `payment_intents` fresh/upgrade migration on SQLite+PostgreSQL, reusing the existing globally-unique `uuid` as the attempt UUID and using the portable unique `(tenant_uuid,gateway,reference)` constraint (both drivers permit multiple NULL references); initializing timeout/crash retry with the same attempt; deterministic failure freeing the active port; duplicate reference rejection; reference-aware confirmation (webhook for superseded attempt closes THAT row; open attempt untouched); one-open-attempt serialization under concurrent renewal; per-attempt idempotency (retry same session, confirmed renewal new attempt); Payvia-level exact-reference dispatch through a recording handler; Commerce-level double-settlement refusal against the paid-order CAS on a real Stripe supersession fixture; Stripe status→expire→re-fetch state table (completed/open/transport-fail/unparseable never free the intent); Stripe+Paystack provider-host URL validation including hostile URL shapes.
**Commerce:** mint conflicts (non-admin-origin, non-pending, cross-tenant); concurrent mint ⇒ one active link (locked-order serialization); regenerate revokes prior; TTL clamp; token shape-gate; resolve indistinguishability (unknown/malformed/cross-tenant); engine LinkView exclusion list (seed store identity + PII sentinels, assert absent); payment-link return provider absent/insecure cases fail before provider I/O and PayableReference metadata contains signed handles but never raw token; fixed-window initiation counter (boundary/reset/concurrency, deterministic clock) atomically enforced before provider I/O; a blocking fake collector proving revoke completes while provider I/O is in flight (no DB lock held) and Phase B then refuses redirect; manual/missing/malformed initiation never redirects; sweep races for mint AND initiation; uninitiated expiry returns to ordinary sweep; issued-session expiry/revoke stays draft-blind and blocks automatic stock release; shared cancellation-guard inventory; admin cancel refuses without risk acknowledgement and records it atomically when accepted; lazy + eager terminal transitions; raw-token no-egress ratchet (grep-style + response assertions); order-before-link lock order documented + concurrency-tested.
**Thallo:** landing state matrix + headers on GET and POST + generic 404 triple; CSRF guard on initiate; 303 only to validated HTTPS gateway URLs; IP rate limit; unavailable/manual path has no `Location`; signed return/cancel purpose separation, hostile signature/shape tests, generic projection and proof that the existing guest-cookie confirmation route is never selected; engine catalog mint/revoke/status mounted once with the host public-URL provider (route-uniqueness test); admin card flows (one-time custody, current-send engine-authoritative token match with exact 404/409 split, Regenerate-and-send confirmation, delivery-failure keeps link + returns URL, same-key replay/different-fingerprint/300-second crash-indeterminate send cases); delivery migration fresh/upgrade on both drivers plus purge/adoption; PaymentRequestMailer persistence audit (notification/queue tables empty of tokens; delivery receipt shape exact); missing rich email channel degradation and mandatory `email_available` meta field; template toggle default-off from pack config + `action_url` substitution; canonical-origin absolute URLs (never request Host); both lease/exposed-session warnings visible in UI; allowlist/parity/openapi/schema gates; full suites all repos.
